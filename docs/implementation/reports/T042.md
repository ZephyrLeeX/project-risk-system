## DESIGN_GAP / Independent Review failure

ADR 0027 规定 hold 的具体人工管理 surface 属于 T042，但没有批准 URL、request/response envelope、失败
shape 或既有 `/api` compatibility contract。T042 的 stop condition 明确要求遇到此类未批准 public contract
时停止，故不得自行新增 hold API。需要新的 ADR/addendum 明确该 surface，才可继续。

Independent Review 还发现候选实现的两个必须在恢复 T042 后修复的持久化语义缺陷：

- `create()` 与 `release()` 对 resource advisory lock 和 hold row lock 的取得顺序相反；同一资源并发
  create/release 可能死锁，未满足 ADR 0027 的串行化要求。
- 现有表约束未在数据库层阻止终态 `RELEASED`/`EXPIRED` 行被清空终态字段后重新写为 `ACTIVE`；需要不可绕过的
  transition/immutability enforcement。

`AgentConversation` 的新字段已由 revision 回填并纳入模型，但创建路径属于后续 T028 write-set，T042 不得
跨 Task 实现。恢复时需确保已批准的 T028 创建路径使用 T042 的冻结策略接口。

## 2026-08-12 DESIGN_GAP resolution

ADR 0027 的 approved addendum 已冻结人工 hold 管理 API：`POST/GET /api/admin/retention-holds`、
`GET /api/admin/retention-holds/{holdId}` 与 `POST /api/admin/retention-holds/{holdId}/release`，均使用既有
envelope、Cookie/CSRF、`admin.config.manage` 和明确的 validation/not-found/conflict machine codes。它还明确：

- `RELEASED`、`EXPIRED` 为不可重新激活的终态；再次保全只能创建新行，且 PostgreSQL trigger/partial unique
  index 必须强制该不变量。
- create、release、到期和清理复核统一采用 resource advisory lock → resource fact row lock → hold row lock 的
  PostgreSQL 顺序；按 hold ID release 只能先无锁定位，随后必须按该顺序重新读取。
- exact active create retry 与 already released release retry 是无额外审计的幂等成功；不同 active create、
  expired/terminal release 和未获批准的 `BACKUP_COPY` surface 是固定冲突。
- 成功、失败及自动到期只使用 ADR 0017 的 fixed metadata-only audit actions，不携带正文、文件名、自由文本或
  JSON metadata。

因此 T042 由 `DESIGN_GAP` 恢复为 `READY`。这不是候选实现的 accept、re-review 或 code checkpoint；现有未提交
候选代码仍必须在恢复实施时按 addendum 修复、验证并独立 Review。Wave 11 保持 `IN_PROGRESS`，未启动 Integration；
DG-05、DG-08 仍未处理。
