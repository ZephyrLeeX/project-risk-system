# 第二阶段第7步：已解除风险

> 历史实现说明：本文中的“审计快照”已由 ADR 0017 取代。正式 FastAPI Audit 仅保存固定 typed
> metadata；解除原因保存在正式业务时间线中，不复制到 Audit payload。

## 1. 完成结论

“已解除风险”已由静态占位模块升级为真实业务闭环。风险管理员可以在风险详情中
填写解除原因并解除风险，也可以在历史记录中填写原因重新打开风险。

风险状态、关联待办、时间线事件和审计日志在同一数据库事务中更新，任一环节失败
都会整体回滚。

## 2. 状态转换规则

### 2.1 解除风险

- 操作人必须具备 `risk.resolve`；
- 风险必须处于 `ACTIVE`；
- 解除原因必填，去除首尾空格后长度为5至2000个字符；
- 状态更新为 `RESOLVED`；
- 记录解除时间、解除人和完整解除原因；
- 未完成的关联待办同步更新为“已完成”；
- 关联待办保留原处理说明，并追加风险解除说明；
- 追加 `ACTION_COMPLETED` 和 `RISK_RESOLVED` 时间线事件；
- 写入 `RISK_RESOLVED` 审计日志。

重复解除已解除风险会返回业务错误，不会产生重复事件或审计。

### 2.2 重新打开风险

- 操作人必须具备 `risk.resolve`；
- 风险必须处于 `RESOLVED`；
- 重新打开原因必填，长度为5至2000个字符；
- 状态恢复为 `ACTIVE`；
- 清空当前解除时间、解除人和解除原因；
- 已有关联待办恢复为“待处理”，并清空当前完成标记；
- 如果历史风险没有关联待办，按风险等级和项目负责人规则重新生成；
- 追加处理推进或待办生成事件，以及 `RISK_REOPENED` 时间线事件；
- 写入 `RISK_REOPENED` 审计日志。

前一次解除原因继续保存在风险解除时间线事件和审计快照中，不因重新打开而丢失。

## 3. 已解除风险列表

列表只查询当前状态为 `RESOLVED` 且位于当前用户项目数据范围内的风险。

展示字段：

- 风险描述和原始来源；
- 项目名称与项目负责人；
- 原风险等级；
- 原风险类别；
- 解除时间和解除人；
- 完整解除原因。

筛选条件：

- 项目、风险描述或解除原因关键词；
- 原风险等级；
- 原风险类别；
- 项目负责人；
- 分页。

点击任一记录可查看原风险描述、证据、建议措施、项目与回款信息、解除时间、
解除人、解除原因和同项目其他风险。

## 4. 接口

### 4.1 已解除风险列表

`GET /api/risks/resolved`

查询参数：

- `keyword`
- `level`
- `categoryId`
- `owner`
- `sourceType`
- `page`
- `pageSize`

### 4.2 解除风险

`POST /api/risks/:id/resolve`

请求体：

```json
{
  "reason": "已完成处置并取得相关方书面确认，风险影响已消除。"
}
```

### 4.3 重新打开风险

`POST /api/risks/:id/reopen`

请求体：

```json
{
  "reason": "收到新的异议材料，需要恢复风险跟踪并重新评估。"
}
```

### 4.4 风险详情

`GET /api/risks/:id`

详情新增返回 `resolvedByName`，并继续返回 `resolvedAt` 和
`resolutionReason`。

## 5. 权限与数据范围

- 列表和详情校验 `dashboard.view`；
- 解除和重新打开校验 `risk.resolve`；
- 所有查询与变更均应用当前用户项目数据范围；
- 即使知道风险ID，也不能操作超出数据范围的风险；
- 只读查看/审计员可查看授权范围内的已解除风险，但解除操作返回403；
- 前端根据权限隐藏解除和重新打开操作入口，后端权限守卫仍是最终安全边界。
